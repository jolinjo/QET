# PDM 離線鎖定設計:超過 N 天未連線內網即降為瀏覽模式

> 狀態:**設計討論,尚未實作**。本文記錄需求、安全設計與分階段實作計畫。
> 相關:`pdm-gitea-admin-guide.md`、`pdm-gitea-dev-plan.md`。

## 1. 需求

若 QET 客戶端**超過 N 天(預設 10 天)未成功連線內網 PDM**,程式自動降為
**唯讀瀏覽**:

- 不能進入編輯模式
- 不能新增 / 開啟任意本機 .qet
- 僅能瀏覽 PDM 唯讀內容

目標是「不易被繞過或破解」。

## 2. 先認清天花板

**純客戶端的檢查理論上一定能被破解**——程式跑在使用者機器上,他掌握二進位、
檔案、時鐘、網路。務實目標不是「無法破解」,而是:

- 讓**一般員工**(非專業逆向)覺得不值得花力氣繞;
- 讓**繞過也拿不到好處**(這才是真正的防線,見 §6)。

威脅模型:內部員工想離線持續編輯以規避 PDM 出庫/鎖定紀律;可能會改系統
時鐘、改設定檔、(少數)patch 二進位。非國家級對手。

## 3. 核心機制:伺服器**簽章**的心跳 token

不要用「客戶端自己記上次連線時間」——純文字誰都能改。改成:

**每次成功連上內網 PDM,由伺服器發一張有簽章的通行證:**

```
payload   = { sub: <gitea_login>, iat: <伺服器時間>, exp: iat + N天 [, dev: <device_id>] }
signature = Ed25519_sign(私鑰, payload)
```

- **私鑰只在伺服器**,公鑰**編進 app**。
- 客戶端啟動 / 要進編輯模式時:驗簽章 + 檢查 `exp > now`。
- 使用者**無法偽造一張到期日更晚的 token**(沒有私鑰簽不出來)。

這把「想繼續編輯」唯一的合法路徑,逼回「真的去連伺服器拿新 token」——正是要
的效果。

> 用 **Ed25519(非對稱)**,不要用 HMAC:HMAC 的密鑰得放進 app,被逆向抽出
> 就能自己偽造;Ed25519 app 只帶公鑰,再怎麼逆向也簽不出有效 token。

## 4. 最大攻擊面:改系統時鐘

即使 token 不能偽造,使用者可把時鐘**調回過去**,讓 `now < exp` 永遠成立。防禦:

- **單調高水位(high-watermark)**:另存「我看過的最大時間」。每次啟動比對,
  若目前時鐘 < 高水位 → 判定回撥 → 直接鎖。
- **用伺服器時間當錨**:每次連線拿 HTTP 回應的 `Date` header(或一支 API)當
  可信的伺服器時間,寫進高水位。本機時鐘怎麼調都有外部參照。
- 往前調時鐘對他沒好處(token 反而更快過期);往後調被高水位抓到。

## 5. 儲存與防竄改

- token + 高水位放 **macOS Keychain**(比純檔案難改),不要放可讀寫的
  QSettings / 純文字。
- 就算改了 Keychain 內容,**簽章驗不過就無效**——真正保護 token 的是簽章,
  不是儲存位置。
- 高水位可多存幾處交叉比對(Keychain + 一個雜湊過的檔),取最嚴格值。

## 6. 最強的一招:把「價值」綁在伺服器(已具備)

比任何客戶端檢查都硬:**讓有價值的動作本質上就需要伺服器**。PDM 已經是這樣:

- 出庫要 `lfs lock`(伺服器)
- 入庫要 `push`(伺服器)
- 發行要合併受保護分支(伺服器)

所以就算有人 patch 掉本機「瀏覽模式旗標」硬開編輯,他**還是不能出庫/入庫/
發行**,改的只是本機亂畫、永遠進不了圖庫。**破解收益幾乎是零**。10 天鎖定主要
是「政策提醒 + UX」,真正的閘門是伺服器,而那個繞不過。

## 7. 簽章端點架構(sidecar)

最省事:**一支獨立小服務,塞進 Gitea 現有的 docker-compose,同一 Docker
網段**。它不自建帳號——**認證委派給 Gitea**。

流程:

1. 客戶端 → 簽章端點:帶著本來就有的 **Gitea token**(`Authorization: token …`)。
2. 簽章端點 → Gitea(內部 `gitea:3000`):`GET /api/v1/user` 驗這個 token。
3. 驗過(拿到 `login`)→ Ed25519 簽 `{sub, iat, exp}` → 回傳。
4. 客戶端用內建公鑰驗簽 + 檢查 `exp`。

好處:誰能拿 token = 誰在 Gitea 有帳號;離職停用 Gitea 帳號即自動失效
(符合「QET 不自建帳號」原則)。

技術選型:

- **語言 Go**:單一靜態 binary、無 runtime 依賴、Ed25519 在標準庫、`net/http`
  即可,整支約 40~60 行,容器可 `FROM scratch`。
- **對外**:最省事開獨立 port(如 `hc-server:3001/token`);有反代則把 `/token`
  路由到它、其餘到 Gitea。
- **金鑰**:`openssl`/Go 產一次 keypair;私鑰放伺服器(Docker secret 或
  `chmod 600`+環境變數,**絕不進版控**);公鑰當常數編進 app。換金鑰=產新對+
  換 app 公鑰+發一版 OTA。

其他安全細節:

- **私鑰外洩 = 全破**,檔案權限/secret 管理是重中之重。
- **HTTP 重放**:內網目前 HTTP,token 被側錄可在 N 天內被冒用;要更嚴可在
  token 綁 **device_id**(客戶端首次產生存 Keychain,簽進 token),token 不能
  跨機器分享。

## 8. 客戶端整合

- Qt 無內建 Ed25519。用 **libsodium**(`crypto_sign_verify_detached`,乾淨小巧)
  或 OpenSSL EVP(QtNetwork 已連 OpenSSL 1.1.1+,支援 Ed25519,但 API 較繁)。
- **心跳整合點**:現有 `verifyConnection`(打 Gitea `/user`)成功後,順手去簽章
  端點換新 token,存 Keychain + 更新高水位。
- **降級**:到期 → 進唯讀瀏覽,接現成的 `applyReadOnlyView` / 模式鈕隱藏
  (禁編輯模式、禁新增/開新檔)。

## 9. 分階段實作計畫

原則:**先做最難、最能獨立驗證的部分;強制之前先「只觀察不鎖」;盡量重用既有
唯讀基礎設施**。

- **Phase 0 — 決策與前置(無程式碼)**
  - 定案政策:N=10?誰能合理離線?誤鎖如何救?
  - 定案 token 格式、要不要綁 device_id;產 Ed25519 金鑰對。

- **Phase 1 — 簽章端點(server,獨立可測)**
  - Go sidecar:驗 Gitea token → 簽 `{sub, iat, exp}`。
  - 進 docker-compose、金鑰管理。
  - **純 curl 驗證**,完全不碰客戶端。這是支點,先獨立做完。

- **Phase 2 — 客戶端「心跳 + 儲存」(只記錄、不強制)**
  - 連線成功後拿 token,驗簽,存 Keychain;存高水位(伺服器時間)。
  - UI 顯示「上次心跳 / 剩餘天數」,但**先不鎖**。
  - 目的:讓機制先跑一段,確認不會誤判(時鐘、網路、出差)。

- **Phase 3 — 降級強制(接唯讀模式)**
  - 到期 → 唯讀瀏覽(`applyReadOnlyView`);到期前黃色橫幅提醒。
  - 時鐘回撥偵測 → 鎖。
  - **前面都驗證過才開強制。**

- **Phase 4 — 韌性與後門**
  - 管理員離線碼(私鑰簽的短期臨時 token),給合理離線者,避免正當使用者被卡死。
  - 邊界處理:伺服器維護、換機器、token 損毀的優雅降級。

- **Phase 5 —(可選)反竄改加固**
  - 啟動時關鍵函式自我完整性檢查等。CP 值低(見 §2/§6),誠實評估後再決定。

**為什麼是這個順序**:Phase 1 先把加密 + Gitea 委派這塊最不確定的獨立做完可測;
Phase 2「只觀察」先於 Phase 3「強制」——絕不能一上線就在第 10 天誤鎖正當使用者;
Phase 3 重用既有唯讀基礎設施;Phase 4 的管理員後門要在推廣前就位。

## 10. 工作量粗估

- 簽章端點(server):~1~2 小時。
- 客戶端(libsodium、Keychain、驗簽+高水位、接唯讀降級與心跳):~1 天。
- 不含 Phase 0 決策與 Phase 4/5。
